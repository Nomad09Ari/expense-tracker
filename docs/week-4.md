# Долоо хоног 4 — Хэрэглэгч ба өгөгдлийн сан

## Өнгөрсөн долоо хоногийн асуулт

Найздаа линкээ илгээвэл тэр **чиний бүх зардлыг харна.** Мөн бүгдийг нь устгаж чадна.

Учир нь `GET /api/expenses` нь файл дотор байгаа бүгдийг л буцаадаг. Хэн асууж байгааг
асуудаггүй, учир нь **асуух чадваргүй** — сервер хэн ч болохыг мэдэхгүй.

Одоогийн байдлаар апп чинь нэг том хамтын дэвтэр. Хүн бүр ижил хуудсан дээр бичиж байна.

Энэ долоо хоногт хоёр зүйл нэмнэ:
- Сервер **чи хэн бэ** гэдгийг мэддэг болох
- Мөр бүр **эзэнтэй** болох

> Prompt бичих зарчим: [Claude-тай хамт код бичих](claude-ashiglah.md)

---

## Ойлголт 1 — Хоёр өөр асуулт

Эдгээрийг хольж хутгах нь маш түгээмэл. Хоёр тусдаа асуулт:

| | Асуулт | Англи нэр | Алдааны код |
|---|---|---|---|
| **①** | Чи хэн бэ? | Authentication | `401` |
| **②** | Чи үүнийг хийж болох уу? | Authorization | `403` |

Нэвтрэх систем нь **①**-ийг л шийддэг. Ихэнх хүн тэгээд болсон гэж боддог.

Гэтэл жинхэнэ аюул **②**-т байна. Хэрэглэгч А нэвтэрсэн байж болно — гэхдээ хэрэглэгч
Б-гийн зардлыг устгах гэж байвал? Сервер `id`-г нь харах бүрдээ "энэ мөр хэнийх вэ?
Асууж байгаа хүнийх мөн үү?" гэж **шалгах ёстой**.

Энэ шалгалт дутсанаас болж жинхэнэ аппуудад жил бүр дата алдагддаг. Энэ долоо хоногийн
хамгийн чухал зүйл нь нэвтрэх форм биш — **тэр шалгалт.**

## Ойлголт 2 — Нууц үгийг хэзээ ч хэвээр нь хадгалдаггүй

### Асуудал юу вэ

```json
{ "email": "bat@example.com", "password": "hello123" }
```

Хэн нэгэн өгөгдлийн санд хандвал бүх нууц үг гартаа орно. Хүмүүс ижил нууц үгийг
олон газар хэрэглэдэг тул чиний жижиг зардлын аппаас болж тэдний банк, шуудан алдагдана.

Энэ бол таамаг биш. Жил бүр болдог.

### Хэрхэн шийддэг вэ

Нууц үгийг **hash** хийж хадгална. Hash гэдэг нь буцаагдашгүй хувиргалт:

```
"hello123"  →  "$2b$10$N9qo8uLOickgx2ZMRZoMye..."
```

Гурван шинж чанартай:
- Ижил нууц үг үргэлж ижил hash өгнө
- Hash-аас нууц үгийг **буцааж гаргах боломжгүй**
- Нэг үсэг өөрчлөгдвөл hash бүхэлдээ өөр болно

Нэвтрэхэд юу болох вэ: илгээсэн нууц үгийг мөн hash хийгээд, хадгалсан hash-тай
харьцуулна. Хоёр таарвал зөв. **Сервер жинхэнэ нууц үгийг хэзээ ч мэдэхгүй.**

```js
import bcrypt from "bcryptjs";

// Бүртгүүлэхэд
const hash = await bcrypt.hash(password, 10);

// Нэвтрэхэд
const ok = await bcrypt.compare(password, user.passwordHash);
```

Тэр `10` нь хэр удаан бодох вэ гэдгийг заана. Том тоо = удаан = таах гэж оролдоход
хэцүү. `10` бол сайн анхны утга.

### Түгээмэл буруу ойлголт

**"Hash хийхийн оронд шифрлэвэл болохгүй юу?"**

Шифрлэлт нь **буцаагддаг** — түлхүүр байвал уншина. Тэгвэл түлхүүр алдагдвал бүх нууц
үг задарна. Hash нь буцаагддаггүй тул түлхүүр гэж байхгүй, алдагдах зүйл ч байхгүй.

## Ойлголт 3 — Сервер чамайг яаж санадаг вэ

### Асуудал юу вэ

HTTP бол **санах ойгүй.** Хүсэлт бүр цоо шинэ. Сервер өмнөх хүсэлтийг санадаггүй.

Тэгвэл нэвтэрсний дараа дараагийн хүсэлт дээр яаж таньдаг юм бэ?

### Хэрхэн шийддэг вэ

Нэвтрэхэд сервер санамсаргүй урт мөр (**token**) үүсгээд хадгална:

```
token "9f2a...c1" → хэрэглэгч bat@example.com
```

Тэр token-г хөтөч рүү **cookie** болгож илгээнэ. Хөтөч түүнийг хадгалж аваад,
цаашид тухайн сайт руу явуулах **хүсэлт бүрт автоматаар хавсаргана**.

```
Хөтөч                                 Сервер
  │  POST /api/auth/login              │
  │  { email, password }         ────► │  Нууц үг таарлаа
  │                                    │  token үүсгээд хадгаллаа
  │  ◄──── Set-Cookie: session=9f2a…   │
  │                                    │
  │  GET /api/expenses                 │
  │  Cookie: session=9f2a…       ────► │  token → bat@example.com
  │                                    │  Батын зардлуудыг л буцаана
  │  ◄──── [ ... ]                     │
```

### `httpOnly` яагаад чухал вэ

Cookie-г тавихдаа ингэж тэмдэглэнэ:

```js
cookies().set("session", token, {
  httpOnly: true,   // JavaScript уншиж чадахгүй
  secure: true,     // зөвхөн HTTPS-ээр явна
  sameSite: "lax",  // өөр сайтаас илгээгдэхгүй
  maxAge: 60 * 60 * 24 * 7,   // 7 хоног
});
```

`httpOnly: true` нь **хамгийн чухал нь**. Энэ тохиргоотой cookie-г хуудсан дээрх
JavaScript уншиж чадахгүй — зөвхөн хөтөч өөрөө сервер рүү явуулна.

Яагаад хэрэгтэй вэ: чиний хуудсанд ямар нэг байдлаар хорлонтой скрипт орж ирвэл
(жишээ нь хэрэглэгчийн бичсэн текстээр дамжин), тэр скрипт token-г уншиж хулгайлж
чадахгүй.

> **`localStorage`-д token хадгалж болох уу?** Олон заавар тэгэхийг зөвлөдөг. Гэхдээ
> `localStorage`-г JavaScript ямар ч үед уншина — дээрх хамгаалалт байхгүй.
> `httpOnly` cookie нь илүү аюулгүй, бас илүү хялбар (гараар хавсаргах шаардлагагүй,
> хөтөч өөрөө хийнэ).

### Next.js-д cookie ажиллуулах

```js
import { cookies } from "next/headers";

export async function POST(request) {
  const cookieStore = await cookies();     // await анзаараарай
  cookieStore.set("session", token, { httpOnly: true, ... });
  return Response.json({ ok: true });
}
```

Уншихдаа:

```js
const cookieStore = await cookies();
const token = cookieStore.get("session")?.value;
```

## Ойлголт 4 — Дата хэнийх вэ

Энэ бол долоо хоногийн гол хэсэг.

### Хоёр хүснэгт, нэг холбоос

```
users                          expenses
─────                          ────────
id        "u1"                 id        "e1"
email     "bat@..."            amount    12000
password  "$2b$10$..."         category  "food"
                               userId    "u1"   ◄── ЭНЭ
```

`userId` нь тухайн мөр хэнийх болохыг заана. Үүнийг **холбоос (relation)** гэнэ.
Өгөгдлийн санд хамгийн чухал ойлголтуудын нэг: хүснэгтүүд бие биенээ заадаг.

### Шалгалт хаана байх ёстой вэ

Одоо чухал хэсэг. Энэ шалгалт **route handler бүрт** байх ёстой:

```js
// GET — зөвхөн өөрийнхийг нь буцаана
const user = await getCurrentUser();
if (!user) return Response.json({ error: "Нэвтрээгүй байна" }, { status: 401 });

const mine = await db.getAllByUser(user.id);
return Response.json(mine);
```

```js
// DELETE — эзэн нь мөн эсэхийг шалгана
const user = await getCurrentUser();
if (!user) return Response.json({ error: "Нэвтрээгүй байна" }, { status: 401 });

const expense = await db.getById(id);
if (!expense) return Response.json({ error: "Олдсонгүй" }, { status: 404 });

if (expense.userId !== user.id) {
  return Response.json({ error: "Эрх байхгүй" }, { status: 403 });
}

await db.remove(id);
```

Тэр `expense.userId !== user.id` гэсэн гурван мөр л чиний хэрэглэгчдийн датаг
хамгаалж байна.

### Түгээмэл буруу ойлголт

**"Frontend дээр нь өөр хүний зардлыг харуулахгүй бол хангалттай."**

Огт хангалтгүй. Frontend бол зөвхөн харагдац. Хэн ч `requests.http`, `curl`, эсвэл
энгийн скриптээр чиний API руу шууд хүсэлт илгээж чадна — чиний хуудсыг огт нээхгүйгээр.

**Frontend бол хэрэглэгчийн тав тухын төлөө. Хамгаалалт зөвхөн серверт байдаг.**

Үүнийг өөрөө туршиж үзэх дасгал доор байна.

## Ойлголт 5 — Яагаад өгөгдлийн сан хэрэгтэй вэ

2 дахь долоо хоногт JSON файл Vercel дээр ажиллаагүйг санаж байгаа биз. Тэр бол
шалтгааны нэг нь л. Бас гурав бий:

**① Зэрэг бичих.** Хоёр хүн нэг зэрэг зардал нэмвэл: хоёулаа файлыг уншина, хоёулаа
нэг мөр нэмнэ, хоёулаа бичнэ. Хоёр дахь бичилт эхнийхийг дарж бүрэн устгана. Нэг
зардал алга болно. Өгөгдлийн сан үүнээс сэргийлдэг.

**② Хайх.** Файлын арга нь бүх датаг санах ойд ачаалж, дараа нь `filter` хийдэг.
100 зардалд асуудалгүй. 100,000 зардалд сервер унана. Өгөгдлийн сан нь **индекс**
ашиглан огт өөр аргаар хайдаг.

**③ Холбоос.** `userId` бол холбоос. Өгөгдлийн сан үүнийг ойлгодог: хэрэглэгчийг
устгавал түүний зардлыг яах вэ гэдгийг чи зарлаж өгч чадна, мөн байхгүй хэрэглэгч
рүү заасан зардал үүсэхээс сэргийлнэ.

### Prisma гэж юу вэ

Өгөгдлийн сантай SQL бичихгүйгээр ярилцах багаж. Датаныхаа хэлбэрийг нэг файлд
тодорхойлно:

```prisma
model User {
  id        String    @id @default(cuid())
  email     String    @unique
  password  String
  expenses  Expense[]
}

model Expense {
  id       String   @id @default(cuid())
  amount   Int
  category String
  note     String?
  date     DateTime
  userId   String
  user     User     @relation(fields: [userId], references: [id], onDelete: Cascade)
}
```

Уншиж ойлгоход амархан:
- `@unique` — хоёр хэрэглэгч ижил и-мэйлтэй байж болохгүй
- `String?` — асуултын тэмдэг нь "хоосон байж болно" гэсэн үг
- `expenses Expense[]` — нэг хэрэглэгч олон зардалтай
- `onDelete: Cascade` — хэрэглэгч уствал зардлууд нь ч устана

Дараа нь:

```js
const mine = await prisma.expense.findMany({ where: { userId: user.id } });
```


## Даалгавар 4.2 — Дата эзэнтэй болгох

**Зорилго:** хэрэглэгч бүр зөвхөн өөрийнхөө датаг харах, өөрчлөх.

**Тулгуурлах ойлголт:** Ойлголт 4

**Алхмууд**

1. `data/expenses.json` доторх бүх мөрөнд `userId` талбар нэм.
2. `lib/db.js`-ийн функцүүдийг `userId` хүлээж авдаг болго.
3. `app/api/expenses/route.js`:
   - `GET` → зөвхөн одоогийн хэрэглэгчийнх
   - `POST` → шинэ зардалд одоогийн хэрэглэгчийн `id`-г тавина
4. `app/api/expenses/[id]/route.js`:
   - `DELETE`, `PATCH` → эзэн нь мөн эсэхийг шалгана, биш бол `403`
5. Нэвтрээгүй бол бүх endpoint `401` буцаана.

**Claude-д өгөх prompt-ын жишээ**

```
Next.js App Router, JavaScript. lib/session.js дотор getCurrentUser() бэлэн байгаа.

Зардлуудыг хэрэглэгч тус бүрд харьяалуулна.

1. lib/db.js:
   - getAllByUser(userId)
   - getById(id)
   - create(expense) — expense дотор userId байна
   - remove(id), update(id, changes)

2. app/api/expenses/route.js:
   - GET: getCurrentUser() null бол 401. Үгүй бол getAllByUser(user.id) буцаана.
   - POST: 401 шалгалт. Шинэ зардалд userId-г СЕРВЕР ДЭЭР тавина —
     хүсэлтийн body-с ирсэн userId-д хэзээ ч бүү итгэ.

3. app/api/expenses/[id]/route.js — DELETE, PATCH хоёулаа:
   - getCurrentUser() null бол 401
   - Зардал олдоогүй бол 404
   - expense.userId !== user.id бол 403
   - Бүгд таарвал л үйлдлээ хийнэ

Хязгаарлалт:
- Шалгалт нь СЕРВЕРТ байна. Frontend дээрх нуулт хамгаалалт биш.
- Одоо байгаа data/expenses.json доторх мөрүүдэд userId нэмэх шаардлагатай.
```

> "body-с ирсэн userId-д бүү итгэ" гэсэн мөр нь хамгийн чухал нь. Хэрэв сервер
> хүсэлтэд бичигдсэн `userId`-г шууд авбал хэн ч өөр хүний нэрээр зардал үүсгэж чадна.
> Хэн болохыг **зөвхөн cookie** шийднэ.

**Гарсан кодыг шалгах**

- [ ] `userId` нь `getCurrentUser()`-с ирж байна, `request.body`-с **биш**
- [ ] `GET` дээр `getAllByUser` ашигласан, бүгдийг татаад frontend дээр шүүгээгүй
- [ ] `DELETE`, `PATCH` хоёулаа эзний шалгалттай
- [ ] `401` (нэвтрээгүй) болон `403` (эрхгүй) ялгаатай хэрэглэгдсэн
- [ ] Endpoint бүр `getCurrentUser()`-с эхэлж байна — нэг ч алгасаагүй

**Дууссан гэж үзэх шалгуур**

- [ ] Хэрэглэгч А нэвтэрч 2 зардал нэмнэ
- [ ] Гараад хэрэглэгч Б-гээр бүртгүүлж нэвтэрнэ → **хоосон жагсаалт харагдана**
- [ ] Б зардал нэмнэ → зөвхөн өөрийнх нь харагдана
- [ ] А руу буцаж нэвтрэхэд түүний 2 зардал байсан хэвээрээ
- [ ] Cookie устгаад `/api/expenses` нээхэд `401`

### 🔍 Хамгийн чухал дасгал — өөрийгөө халд

Одоо frontend огт ашиглахгүйгээр өөрийн API-гаа шалгана.

**1.** Хэрэглэгч А-гаар нэвтэр. Нэг зардал нэм. Network таб дээрээс түүний **`id`**-г ол.

**2.** Гар. Хэрэглэгч Б-гээр нэвтэр.

**3.** `docs/requests.http` дээр ийм хүсэлт бич:

```http
DELETE http://localhost:3000/api/expenses/<А-ГИЙН ЗАРДЛЫН ID>
```

**4.** Илгээ.

**`403` ирэх ёстой.** Мөн А-гийн зардал устаагүй байх ёстой.

Хэрэв `204` ирж, зардал устсан бол — чиний эзний шалгалт дутуу байна. Олоод зас,
дараа нь дахин турш.

> Энэ дасгалыг заавал хий. Нэг ч хэрэглэгчийн нүд хүрэхгүй газраас чиний API руу
> хандах боломжтой гэдгийг өөрийн гараар мэдрэх нь хэдэн зуун мөр уншсанаас илүү юм.
> Жинхэнэ аппуудад алдагддаг дата ихэвчлэн яг энэ шалгалт дутсанаас болдог.

  барьсны шагнал.
